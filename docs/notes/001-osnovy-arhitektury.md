## 1. Три сущности ядра

`Reduce(state, action, config, deltaTime)` — в сигнатуре четыре аргумента, и первые три это три разных типа сущностей.

| | Что это | Как часто меняется | Веб-аналог |
|---|---|---|---|
| `FighterState` | данные: что сейчас происходит | каждый тик, 60 раз в секунду | `state` в Redux-сторе |
| `Reduce` | функция: правило перехода | не меняется, это код | редьюсер |
| `FlightConfig` | настройки: числа для тюнинга | когда покрутил ползунок | конфиг-файл, env |

```csharp
public struct FighterState
{
    public Vector3 Position;
    public Vector3 Velocity;
    public Quaternion Rotation;
    public float DashCooldownRemaining;
}
```

```csharp
public class FlightConfig : ScriptableObject
{
    public float MaxSpeed = 40f;
    public float Acceleration = 80f;
    public float VelocityDecay = 3f;
    public float DashDistance = 15f;
    public float DashCooldown = 0.8f;
}
```

Разница `FighterState` и `Reduce` в одну строку: первое — существительное (что есть), второе — глагол (как меняется).

### Почему `FlightConfig` отдельно, а не полями внутри состояния

1. **Разная скорость изменения.** Состояние меняется 60 раз в секунду, конфиг — руками. Смешивать данные с разным жизненным циклом — грязь. Это как положить `API_BASE_URL` в Redux-стор рядом с `currentUser`.
2. **Один на всех.** У двух бойцов два разных `FighterState`, но `FlightConfig` — один ассет на обоих.
3. **Тюнинг в play mode.** `ScriptableObject` — это файл-ассет, отдельный от сцены. Запустил игру, летаешь, и прямо в полёте тянешь ползунок `MaxSpeed` в инспекторе. Сразу чувствуешь разницу, без перезапуска. Аналог: hot reload конфига без рестарта сервера. Для игры про ощущения это главная практическая причина — правильное число находится руками за сотню итераций.
4. **Сеть потом.** Для отката надо гонять состояние. `FighterState` маленький. `FlightConfig` одинаков на всех машинах, передавать не нужно. Смешаешь — будешь слать константы каждый кадр.

## 2. Редьюсер

### Откуда слово

От `reduce` — свёртка массива:

```js
[1, 2, 3, 4].reduce((acc, item) => acc + item, 0)  // 10
```

Функция, которую передаёшь внутрь — `(acc, item) => newAcc` — и есть редьюсер. Сигнатура всегда одна:

```
(накопленное, следующее) -> новое накопленное
```

Больше в слове ничего нет.

### Redux — то же самое, накопленное = состояние приложения

```js
function reducer(state, action) {
  switch (action.type) {
    case 'INCREMENT': return { ...state, count: state.count + 1 }
    default: return state
  }
}
```

Массива не видно, но он есть — это поток действий во времени. Redux — `reduce` по бесконечной ленте действий пользователя.

### Наша игра — тот же `reduce`, лента = кадры симуляции

```
Reduce(state, action, config, deltaTime) -> newState
       ^      ^                              ^
   накоплено  следующий элемент         новое накопленное
```

Псевдокодом на JS, чтобы видеть родство:

```js
const finalState = inputFrames.reduce(
  (state, action) => Reduce(state, action, config, 1/60),
  initialState
)
```

Игра — буквально свёртка списка нажатий в конечное состояние бойца.

### Три правила редьюсера

Не украшения — на них держится всё остальное.

1. **Чистота.** Те же аргументы → тот же результат, всегда. Никаких `Time.deltaTime`, `Random`, `Transform`. Это сторожит тест `Reduce_IsPure_SameInputsProduceSameState`.
2. **Никаких побочных эффектов.** Не пишет в файл, не двигает объекты сцены, не логирует. Считает число и возвращает.
3. **Не мутирует вход.** Возвращает новое состояние. В JS пишешь `{...state}`. В C# проще: `FighterState` — это `struct`, структуры копируются при присваивании автоматически.

### Что это даёт на практике

- **Тесты.** Обычная функция, без сцены и без запуска игры. Миллисекунды.

  ```csharp
  var state = new FighterState { Velocity = new Vector3(10, 0, 0) };
  var result = Reduce(state, PlayerInputFrame.Empty, config, 1f / 60f);
  Assert.Less(result.Velocity.magnitude, 10f);  // скорость гаснет
  ```

- **Сеть.** Есть `initialState` + список нажатий → можно переиграть любой отрезок заново и получить то же самое. Ровно это делает rollback-нетод: пакет от соперника опоздал — откатись на 5 кадров, вставь его ввод, прокрути заново. Возможно **только** если переход состояния — редьюсер.
- **Отладка.** Записал ленту вводов — воспроизвёл баг сколько угодно раз. В обычном игровом коде «один раз странно дёрнулось» не воспроизводится никогда.

## 3. `Update` и `FixedUpdate`

`MonoBehaviour` — базовый класс компонента Unity. Объявляешь метод с зарезервированным именем — Unity сама его вызывает. Никакой регистрации. Как `useEffect`: вызываешь не ты, а фреймворк в нужный момент жизненного цикла.

| | `Update()` | `FixedUpdate()` |
|---|---|---|
| Когда | каждый отрисованный кадр | через равные промежутки времени |
| Интервал | плавает вместе с FPS | фиксированный (у нас 1/60 с) |
| Веб-аналог | `requestAnimationFrame` | `setInterval` |
| Для чего | рисовка, камера, UI | симуляция |

### Нюанс: связь между ними не «один к одному»

Место, где спотыкаются все новички.

Unity накапливает прошедшее время и перед отрисовкой кадра прогоняет столько вызовов `FixedUpdate`, сколько накопилось. Может быть ноль, один или три.

```
FPS 144, тик 60 Гц  ->  кадры чаще тиков  ->  часто 0 вызовов FixedUpdate за кадр
FPS 60,  тик 60 Гц  ->  примерно 1 к 1
FPS 20,  тик 60 Гц  ->  ~3 вызова за кадр, догоняет
```

Отсюда напрямую растёт нужда в интерполяции (раздел 5).

### Почему симуляция обязана жить в `FixedUpdate`

Потому что `deltaTime` становится **константой** — всегда 1/60.

Считать полёт в `Update` — значит давать `Reduce` разный `deltaTime` каждый вызов. Один и тот же зажатый рывок даст разную дистанцию на 144 Гц и на 60 Гц. Игра играется по-разному на разных мониторах.

Для файтинга смертельно, для сетевой игры вдвойне: переиграть чужой ввод невозможно, если шаг времени зависел от загрузки рендера. Весь план с rollback держится на фиксированном шаге.

> **Задача реализации:** *Project Settings → Time → Fixed Timestep* поменять `0.02` (50 Гц) → `0.01666667` (60 Гц). На 2026-08-30 в проекте стоит `0.02`.

## 4. `Bridge`

Название придумано нами, в Unity такого понятия нет. Слой-склейка между чистой симуляцией и движком.

Работа на каждом тике — три шага:

1. собрать ввод: спросить Input System, что нажато, упаковать в `PlayerInputFrame`
2. позвать редьюсер: `Reduce(state, action, config, deltaTime)`
3. положить результат: новое состояние становится текущим

Никаких правил игры внутри. Ни одного `if` про геймплей.

```csharp
public class FighterSimulationRunner : MonoBehaviour
{
    [SerializeField] private FlightConfig config;
    [SerializeField] private PlayerInputReader inputReader;

    private FighterState currentState;
    private FighterState previousState;

    private void FixedUpdate()
    {
        previousState = currentState;

        PlayerInputFrame action = inputReader.ReadCurrentFrame();
        currentState = FlightSimulation.Reduce(currentState, action, config, Time.fixedDeltaTime);
    }
}
```

`[SerializeField]` — атрибут, который показывает приватное поле в инспекторе Unity. Перетаскиваешь туда мышкой ассет `FlightConfig`, и он подставляется в поле. Внедрение зависимости, только не через конструктор, как в NestJS, а через редактор.

### Аналогия

**Bridge — это контроллер в NestJS.**

```
@Controller  ->  Bridge         принял запрос, собрал DTO, позвал сервис
Service      ->  Simulation     здесь вся бизнес-логика
Serializer   ->  View           превратил результат в то, что видит клиент
```

Контроллер не содержит логики. Появилась бизнес-логика в контроллере — запах. Здесь то же правило.

Второй ракурс: **Bridge — это стор**. Хранит текущее состояние и 60 раз в секунду делает `dispatch`. Стор не знает правил, правила в редьюсере.

### Зачем отдельный именованный слой

`Bridge` — единственное место, где разрешено трогать Unity: `Time`, `Input`, `MonoBehaviour`, `[SerializeField]`.

Открыл папку `Bridge/` — увидел все точки контакта с движком разом. Их две штуки и они тонкие. Появится сеть или тесты без движка — менять только эту папку, `Simulation/` не шелохнётся.

## 5. Интерполяция

### Проблема

Монитор 144 Гц, симуляция 60 Гц. За секунду 144 кадра и 60 новых состояний — на большинстве кадров нового состояния просто нет.

Рисовать в лоб:

```
кадр 1: тик был      -> меш в точке A
кадр 2: тика не было -> стоит в A
кадр 3: тик был      -> прыгнул в B
кадр 4: тика не было -> стоит в B
```

Меш то стоит, то прыгает. Микро-заикание, заметное на быстром полёте. Чем выше герцовка, тем хуже.

### Что это

Взять два известных значения и посчитать промежуточное.

```
A = 10, B = 20
alpha = 0    -> 10
alpha = 0.5  -> 15
alpha = 1    -> 20
```

Формула: `результат = A + (B - A) * alpha`. В Unity — `Lerp` (**l**inear int**erp**olation).

### Как применяем

`Bridge` хранит **два** состояния — предыдущий тик и текущий. Вот зачем в его коде `previousState`. `View` каждый кадр рисует меш между ними.

```csharp
public class FighterView : MonoBehaviour
{
    [SerializeField] private FighterSimulationRunner runner;

    private void Update()
    {
        float alpha = Mathf.Clamp01((Time.time - Time.fixedTime) / Time.fixedDeltaTime);

        transform.position = Vector3.Lerp(
            runner.PreviousState.Position,
            runner.CurrentState.Position,
            alpha);

        transform.rotation = Quaternion.Slerp(
            runner.PreviousState.Rotation,
            runner.CurrentState.Rotation,
            alpha);
    }
}
```

- `Time.fixedTime` — момент начала последнего `FixedUpdate`. `Time.time` — момент начала текущего кадра. Их разница, делённая на длину тика, и есть `alpha` от 0 до 1.
- `Clamp01` — обрезать в 0…1 на случай просадок, когда разница вылезет за тик.
- `Slerp` для поворота — **s**pherical, интерполяция по дуге. Иначе на больших углах поворот ускоряется в середине.
- `Update`, а не `FixedUpdate` — рисовка идёт каждый отрисованный кадр.

### Аналогия

Websocket шлёт координаты 10 раз в секунду, рисуешь 60 FPS. В лоб — объект дёргается. Решение знакомое: держишь два последних пакета и твинишь между ними.

Ближе к вёрстке: CSS `transition`. Меняешь `left` с 10px на 20px одним присваиванием, браузер рисует промежуточные кадры сам. Здесь ты пишешь этот `transition` руками.

### Ключевое следствие для архитектуры

**`transform.position` — не настоящая позиция бойца. Это картинка.**

Настоящая живёт в `FighterState.Position` — обычное поле в структуре, никакого отношения к сцене. `Transform` — то, куда `View` каждый кадр кладёт сглаженное значение для отрисовки.

Отсюда правило: **View никогда не пишет в состояние.** Читает `FighterState`, пишет в `Transform`. Стрелка строго в одну сторону.

Это ровно React: `render` читает `state` и рисует DOM, но не правит `state`. Начни `View` писать в состояние — симуляция перестанет быть воспроизводимой, и план с сетью развалится.

### Чем платим

Интерполяция рисует **прошлое**. Всегда показывает что-то между предыдущим и текущим тиком, то есть состояние возрастом до 16.7 мс. Лишний кадр задержки между нажатием и реакцией.

Для файтинга ощутимо. Альтернатива — **экстраполяция**: предсказывать вперёд от текущей скорости. Задержки нет, но когда предсказание не сбылось (игрок резко сменил направление) — меш дёргается назад, и это выглядит хуже задержки.

Спека выбрала плавность. Окажется на плейтесте, что управление вязкое — это первое место, куда лезть.

## 6. Журнал решений по именованию

Принято 2026-08-30 в ходе разбора.

### `Step` → `Reduce`

Рассматривались `Action`, `Act`, `Step`, `Advance`, `Reduce`.

- **`Action` отклонён.** Три причины: (а) в Redux-аналогии `action` — это вход, а не функция, и наш вход уже есть — `PlayerInputFrame`; одно слово не может значить и вход, и преобразователь; (б) `System.Action` — встроенный тип делегата в C#, имя двоится; (в) перегрузка, ради которой имя предлагалось, от имени не зависит вообще — перегружается любой метод, если различаются параметры.
- **`Act` отклонён.** Лучше `Action` (глагол, нет коллизии), но не говорит, что делает, и всё ещё тянет в сторону action-как-входа.
- **`Reduce` принят.** Прямая калька Redux, имя в C# свободно, честно называет операцию.

### `FlightTuning` → `FlightConfig`

`Config` понятнее для веб-бэкграунда, `Tuning` — жаргон.

### Параметр `input` → `action`

Тип остался `PlayerInputFrame` (он описывает, из чего action состоит), переименован только параметр — чтобы сигнатура читалась как редьюсер:

```csharp
FighterState Reduce(FighterState state, PlayerInputFrame action, FlightConfig config, float deltaTime)
```

## 7. Шпаргалка: Unity → веб

| Unity | Веб-аналог |
|---|---|
| Scene | страница или роут |
| GameObject | узел DOM |
| Component | хук или сервис, привязанный к узлу |
| MonoBehaviour | React-компонент с `useEffect` |
| Prefab | определение компонента vs его инстансы |
| `Update()` | `requestAnimationFrame` |
| `FixedUpdate()` | тик игрового цикла на `setInterval` |
| `ScriptableObject` | конфиг-файл, инжектится в сервис |
| `[SerializeField]` | DI, но через редактор, а не конструктор |
| asmdef | отдельный пакет в монорепо |
| Simulation | сервис (вся бизнес-логика) |
| Bridge | контроллер NestJS / стор Redux |
| View | render в React |
| `Lerp` | CSS `transition` руками |
