# Проект: Power Fantasy Game (Unity)

## Что это

- Хобби-проект: боевая игра (power sandbox / power fantasy).
- **Unity 6000.0.82f1** (Unity 6 LTS), render pipeline **URP**, ввод **Input System**.
- Жанр ощущений: воздушные дуэли, лок-он на цель, рывки-телепорты, энергетические бласты (как Dragon Ball Sparking! ZERO).
- Roadmap: PvE → 1v1 онлайн → командные бои.
- Визуальное направление: бойцы — светящиеся энергетические сущности без скелетной анимации. Красота через VFX, свет, пост-обработку, а не через рисованный арт.
- Ввод для тюнинга: клавиатура + мышь, код поддерживает аналоговый (геймпад).

## Про пользователя (КРИТИЧНО)

**У пользователя нет опыта в Unity и архитектуре игр. Опыт — fullstack веб: React + NestJS.**

- Любой новый термин из геймдева (prefab, scene, asmdef, Rigidbody, FixedUpdate и т.п.) объясняется сразу, одним-двумя предложениями.
- Объяснять через аналогии с его технологиями:
  - Симуляция `Step(state, input) -> state` = Redux редьюсер; `InputFrame` = action; `FighterState` = state.
  - View-слой (рисовка) = render в React: читает состояние, рисует, не мутирует.
  - `ScriptableObject` = конфиг-ассет, редактируемый в редакторе, как конфиг-файл.
  - `MonoBehaviour` = компонент React: логика привязана к объекту на сцене.
  - `.asmdef` (assembly definition) = граница модуля, как пакет в монорепо.

## Архитектура: три слоя

```
Simulation (чистая логика) 
    ↓ (зависимость в одну сторону)
Bridge (MonoBehaviour, FixedUpdate)
    ↓
View (рисовка, интерполяция, камера, VFX)
```

- **Simulation**: чистые функции и состояние. Можно использовать математические структуры (`Vector3`, `Quaternion`) — это обычные struct, сцена им не нужна. Нельзя: `GameObject`, `Transform`, `Time`, `Physics`, `Input`. Граница держится соглашением, а не компилятором.
- **Bridge**: гонит тики (`FixedUpdate`), собирает ввод, вызывает `Simulation.Step()`.
- **View**: читает состояние, рисует, интерполирует. **Никогда не пишет в состояние.**

Причины: (1) без разделения потом нельзя добавить онлайн без переписи боёвки, (2) логику тестируем отдельно от движка, (3) параметры в `ScriptableObject`, тюнятся в play mode.

## Движение

**Собственная кинематика**, не `Rigidbody` и не `CharacterController`.
- `CharacterController` заточен под наземное движение.
- `Rigidbody` отдаёт управление PhysX, недетерминирован при резких рывках.

Оговорка: есть снапшот/восстановление и ресимуляция, **но не битовая детерминированность** (float может разъезжаться между платформами). Для rollback с синхронизацией состояния достаточно; для lockstep-нетода — нет.

## Правила разработки

### Именование
- Имена типов, методов, полей, ассетов должны быть понятны с первого взгляда.
- Приоритет: смысл > краткость. Не допускаются криптичные сокращения и однобуквенные имена (кроме счётчиков цикла).

### Спеки
- Любая заметная фича начинается со спеки в `docs/specs/`.
- Спека: что делаем, почему, оговорки, открытые вопросы.
- **Открытые вопросы и TBD блокируют реализацию.** Сначала утверждение пользователем, потом код.

### TDD
- Сначала падающий тест, потом реализация.
- Логика симуляции: EditMode-тесты (Unity Test Framework), без сцены.
- Сценарные проверки: PlayMode-тесты.

## Инструментарий

- Бинарные ассеты (текстуры, модели, звук, шрифты): Git LFS (правила в `.gitattributes`).
- `Library/`, `Temp/`, `Logs/` не коммитить (в `.gitignore`).

## Запуск и тестирование

- Play mode в редакторе: быстрое тестирование прямо с `ScriptableObject`-параметрами.
- EditMode-тесты: логика симуляции, запуск через Test Runner.
- PlayMode-тесты: сцены, интеграция, VFX.
